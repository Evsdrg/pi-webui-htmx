## 2. 推荐方案与实施门槛

### O01 合并消息投影的重复解码（优先）

`internal/sessions/store.go:ProjectEntries` 先解外层，再由 `scanLazyBlocks`、`messageRoleAndText`、`assistantError`、`parseUsage`、`toolResultMeta` 多次解同一个 message。原始 profile 中 ProjectEntries 累计占 58.6%，原型约 38.8%。

建议共用消息投影结构，让文本、块类型、用量、工具状态和错误分类消费同一份解码结果。**不要称为整个 JSON 只扫描一次**：自定义 UnmarshalJSON 的嵌套调用与内部验证仍可能重扫字节。

原型未达到可合入标准：把 ToolName/IsError 等字段并进统一结构后，一个错误类型可能让整个 message 清零；旧实现的多个独立 decoder 会局部失败。须对错误类型、null、缺失字段、未知 role、command 回退、usage、重复键建立差分测试，保持旧容错边界。原型曾把 usage 对象交给接收整条 message 的 parseUsage，导致费用消失；已修正，说明正常测试绿不足以证明等价。

### O02 收起态预览有界，正文保持完整（优先）

`internal/presentation/presentation.go` 的 Step.Detail 同时进入工具预览和正文；`src/templates/history.html` 的 `.tool-preview` 实际单行省略。独立 Preview 约 200 字符，使样本 HTML 减少 96980 字节（23.8%），CPU 无稳定额外改善。

正式实现应只遍历截断边界内的 UTF-8，避免为了 200 字符把全文转成 []rune。200 是候选值，需在 390 / 1280×720 / 1920×1080 验证可见效果，不能仅凭 CSS 省略宣称绝对视觉等价。详情、复制和导出不得截断。

不推荐当前原型的正文 4K 截断：该样本无体积收益，还新增加载交互。需独立数据支持才考虑。

### O03 惰性内容按已有索引定位（优先）

`internal/sessions/lazy.go:rawEntry` 每次从头读，虽只返回几百字也需约 146 ms。已渲染历史的扫描索引含 offset/size，命中后 ReadAt 单条记录原型约 0.3 ms。适用于 thinking 与图片读取。

正式实现要求：验证读取长度、entryID、消息类型与角色；用打开的文件身份核对缓存，处理 rename/截断/并发改写；保留取消、限额、错误码和完整行语义。**size/mtime/dev/ino 校验不是“绝不可能读旧偏移”的证明**，校验与读取之间仍有竞争窗口。原型未比较返回记录 ID 与请求 ID，不能直接移植。冷路径继续保守扫描；不要把一次未完整验证的局部扫描登记成完整缓存。

### O04 有总预算的小型多会话缓存（随后）

2–4 槽可覆盖 A/B 切换，缓存的是索引而非全文件。必须保留 size/mtime/identity 失效检查，不假设文件只追加。四槽是候选，不是已经量出最佳容量。

现有 `len(nodes)*64` 是粗估，包含字符串内容、map 容量等的可靠保留内存还未测出。RSS 对照曾显示额外 3.4 MiB，也曾显示 7.6 MiB；RSS 含 GC、页驻留、分配器与渲染缓冲差异，**不得推导“每节点 430B / 低估六倍”**。实现前应以强制 GC 后的保留堆差分、节点与字符串字节数建立预算，并测缓存淘汰、并发同文件 miss、过大条目不污染已有缓存。不得把 16 MiB 粗估预算称为严格物理内存上限。

## 3. 其余候选

- 动态压缩（组合版，c=8 / 6秒）：identity 743.8 RPS / 309897B；gzip 713.2 / 61239B；br-4 547.0 / 45974B；br-2 591.0 / 47994B。br-2 比 br-4 体积 +4.4%、吞吐 +8%。这是环回 CPU 对照，未测公网带宽；**不直接宣布 gzip 为公网最佳默认**。静态资源预压缩缓存另论。保持现状，后续有链路数据再选档位。
- 会话列表 stamp：合成扁平36文件约81–83µs，真实8目录约23–25µs。实际布局下优先级低。跳过文件 Info 的原型约77µs且牺牲文件 mtime 变化信号，不推荐。
- WS：之前稳态20k/s已足够，突发时有界摘除慢订阅是背压政策。不要只增加32消息槽掩盖问题；若要优化，先测真实突发分布、恢复路径和总内存。当前无调大建议。
- 不删除 History 的 json.Valid 来追求单次解析：它承担读期间变化检测，与投影跳过坏记录的语义不同。
- Git 部分不研究、不修改。

## 4. 对前次解释与测量的纠正

1. getdents64 直接检查得到 DT_DIR/DT_REG，推翻“f2fs 不返回 d_type”的解释。profile 中有 stat 不能据此判定文件系统缺陷。
2. 目录探针的 strace 没加 -f，Go goroutine 可迁移到其它线程，统计遗漏；1336/2179等计数不能除以200推导每次系统调用数。该组计数废弃。
3. heap profile 头的采样分配数不是精确进程累计分配；此前1562/1505/1472KB每请求不能当精确内存收益。未给出可靠 alloc/op 结论。
4. 旧二进制配新 Preview 模板会返回54字节错误页。那批结果作废；最终 table.sh 同步模板/二进制，并拒绝小于1000字节页面。但未来探针应进一步断言状态码、目标会话及期望内容。
5. 某些测试命令经过 grep/head 管道，末尾“空=全过”不等于退出码证明。研究阶段不把这些输出当正式合入验收，实施时必须保存真实 go test 退出码。
